# 브랜치·커밋·병합

## 기능 작업

- 기능 작업은 기본 브랜치(`main` 등)에서 직접 진행하지 않고, 별도 작업 브랜치를 생성해 진행한다.
- 브랜치를 생성하기 전에 기준 브랜치가 최신 상태이고 워킹 트리가 깨끗한지 확인한다.

## 브랜치 이름

브랜치 이름은 `<작업타입>/<이슈번호>-<작업명>` 형식으로 작성한다. 관련 이슈가 없는 작업은 이슈 번호를 생략하고 `<작업타입>/<작업명>` 형식을 사용한다.

- **작업타입**: `feat`, `fix` 등 작업의 성격을 나타내는 접두사를 사용한다.
- **이슈번호**: 연결된 이슈가 있을 때 작업명 앞에 번호를 표기하고 하이픈(`-`)으로 이어준다.
- **작업명**: 수행하는 작업이 명확히 드러나는 간결한 기능명으로 작성한다.

예시:

- `feat/42-transaction-binding`
- `fix/43-connection-cleanup`
- `feat/transaction-binding` (관련 이슈가 없는 경우)

## 작업 브랜치의 커밋

- 작업 브랜치에서는 변경 의도를 독립적으로 이해하고 검토할 수 있는 가장 작은 단위로 커밋한다. 함께 보아야 의미가 성립하는 변경은 하나로 묶는다.

## 이슈 해결과 관련 자료 참조

이슈 번호가 있는 작업 브랜치의 각 커밋은 해당 번호의 `Refs #번호` 또는 `Closes #번호`를 정확히 일치하는 독립된 줄로 작성한다.

연결할 대상이 있을 때만 커밋 메시지에 아래와 같이 표기한다.

- 이슈 해결: `Closes #24`
- 이슈의 일부 작업 또는 관련 이슈 참조: `Refs #24`
- 관련 커밋 참조: `Refs 43d1cb2`
- 외부 자료 참조: `Refs https://example.com/document`

## revert

변경을 되돌릴 때는 `git revert --no-commit <커밋>` 후 `git commit`을 사용한다. 메시지에는 되돌리는 이유를 작성하고, 이슈 참조는 위 규칙을 따른다.

## 최종 병합

- squash 병합 시 최종 커밋 메시지에도 이슈·관련 자료 참조를 유지한다.
- 하나의 기능을 여러 작은 커밋으로 나누어 작업한 브랜치는 squash 방식으로 병합한다. 병합 전에 squash로 진행할 예정임을 안내하고, 사용자의 승인을 받은 후 진행한다.
- 병합 커밋(`--no-ff`)을 임의로 생성하지 않는다.
