# 설계 원칙

### 설계 제안과 설명

- 설계나 구현 방향을 제안할 때는 **선택 근거**(해결하려는 문제, 대안 대비 기술적 이유와 이점, 트레이드오프)와 **적용 범위**(코어 모듈, 공개 확장 지점과 내부 구현의 경계, `mybatis-winter` 등 외부 연동, `winter-samples` 등)를 함께 설명한다.
- 특정 아키텍처나 패턴을 일괄 강제하지 않으며, 변경이 영향을 미치는 경계를 먼저 정의한 뒤 현재 요구사항을 해결하는 최소한의 구조를 우선한다. 불필요한 추상화나 과도한 제약을 도입하지 않는다.

### 책임과 의존성

- 함께 변경되는 요소는 응집시키고, 변경 이유가 다른 책임은 분리한다.
- 컴포넌트·계층 간 순환 의존을 피하고, 핵심 정책과 추상 계약이 구체적인 구현이나 외부 기술 세부사항에 종속되지 않도록 경계를 둔다.

### 계약과 상태

- 입력·출력·부수효과를 호출자가 내부 구현을 읽지 않고도 계약을 통해 예측할 수 있게 설계한다.
- 상태의 범위와 수명은 필요한 최소한으로 제한하고, 상태 변경의 진입점과 책임을 명확히 한다.
- 파생 상태를 별도로 보관할 때는 계산 비용 등의 필요성과 원본 데이터와의 일관성 유지 방법을 함께 고려한다.

### 실패 처리

- 실패 원인과 진단에 필요한 실행 맥락을 보존한다.
- 복구 정책을 결정할 수 없는 지점에서 실패를 임의로 무시하거나 정상 결과처럼 가리지 않는다.
